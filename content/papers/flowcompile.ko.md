## 세 줄 요약

- LLM을 여러 번 부르는 워크플로우 그래프를 최적화하는 기법인 FlowCompile을 소개 <- 어떤 노드에 어떤 모델을 얼만큼의 예산으로 배정할 것인지, 혹은 그래프에서 어떤 분기를 탈 것인지.
- FlowCompile은 각 노드의 모든 설정값을 미리 돌려서 노드의 프로필을 만들어 둔다. e.g., LLM judge 노드에서 어떤 모델을 쓰면 얼만큼의 비용이 드는지.
- 노드의 프로필을 잘 조합해서 쓸만한 컴파일을 여러 개 마련해 놓고 컴파일별로 성능을 측정해 놓는다. 그리고 나중에 배포할 때마다 적당한 거 하나를 골라서 배포. e.g., 쉬운 문제에서는 적은 예산으로 빠르게 돌아가는 워크플로우 및 노드 설정을 배포한다!

## 요약

### 제안하는 기법: FlowCompile

- 워크플로우 그래프 최적화는 조합적 최적화 문제로 노드와 엣지가 조금만 늘어나도 경우의 수가 폭발적으로 증가. 예컨대, 직렬로 연결된 노드 5개 각각에 설정값이 20개만 있어도 가능한 경우의 수는 320만.
- FlowCompile은 모든 조합을 계산하지 않고 개별 노드의 각 설정값만 미리 계산한다. 그러면 방금 얘기한 그래프에서 노드 5개 각각에서 20개 설정값에 대해서만 계산하면 되니까 총 100번만 계산.
- 계산에서 얻어야 하는 정보는 '소요 시간과 성공률'이다. *(작성자 주. 조금 더 확장하면 '비용과 성능'이라고 봐도 될 듯.)*
- 나중에 소요 시간과 성공률을 갖고 워크플로우의 모든 가능한 경로의 소요 시간과 성공률을 추정. 대략 아래와 같이 계산한다고 보면 됨.

| 그래프 구조                      |            전체 성공률 추정 |         평균 지연시간 추정 |
| --------------------------- | -------------------: | -----------------: |
| A를 실행한 뒤 B를 실행하며 둘 다 성공해야 함 |           $p_Ap_B$ |        $t_A+t_B$ |
| A와 B를 모두 실행하며 하나만 성공해도 됨    | $1-(1-p_A)(1-p_B)$ |        $t_A+t_B$ |
| A가 실패할 때만 B로 재시도            |   $p_A+(1-p_A)p_B$ | $t_A+(1-p_A)t_B$ |

- 이제 모든 경로의 성공률과 평균 지연시간을 추정치로나마 얻었으니 배포할 때마다 마음에 드는 거 하나 선택하면 된다.

### 실험 결과

- FlowCompile의 소요 시간 및 성공률 추정치는 실제 값을 잘 맞추었다.
- MATH-500을 푸는 기본 워크플로우가 있는데 여기에 FlowCompile을 적용하여 모든 가능한 경로의 소요 시간 및 성공률 파악 -> 이후에 성능 우선의 경로를 하나 골라서 실행했더니 성능은 거의 지키면서 소요 시간을 줄일 수 있었다.
